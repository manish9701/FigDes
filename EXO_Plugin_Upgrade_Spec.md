# EXO Design Agent — Plugin Upgrade Specification

## Purpose

Upgrade Design Agent 3 from a strong structured Figma editor into a product-grade UI design agent capable of producing and refining high-fidelity interfaces with the consistency of an experienced senior product designer.

The goal is not more primitive shapes. The goal is better **composition, reusable design systems, semantic editing, visual QA, and iterative refinement**.

---

# 1. Current plugin problems observed

## 1.1 Dynamic-page component access is broken

The plugin currently reports:

> `Cannot call with documentAccess: dynamic-page. Use node.getMainComponentAsync instead.`

This prevents reliable component discovery/reuse in the current EXO Figma document.

### Required fix

Replace synchronous main-component access with the async Figma API path:

```ts
await node.getMainComponentAsync()
```

and make `find_component` work on dynamic-page documents.

This is high priority because the current file reports essentially:

```text
components: 0
variables: 0
styles: 0
```

despite containing many visually reusable structures.

# 3. Semantic node targeting

Current workflows rely too heavily on raw Figma IDs.

Add semantic targeting:

```ts
find_node({
  screen: "V4 Home",
  role: "primaryAction"
})
```

and:

```ts
find_text("Qwen2.5 Coder 72B")
find_by_name("Navigation item")
find_by_role("topologyMap")
```

Example:

```ts
modify({
  targetRole: "activeNavigation",
  fill: "#F2C94C"
})
```

This is dramatically safer than relying on IDs generated by previous transactions.

# 4. Fix design_runtime schema ergonomics

The runtime is the right direction, but the current semantic API is inconsistent.

During EXO testing, these arguments were rejected:

```text
navItem.active
statusPill.state
topologyMap.nodes
button.variant
metric.mono
```

Yet these are natural design concepts that the primitive names strongly imply.

### Required improvement

The schema should support:

```json
{
  "fn": "navItem",
  "args": {
    "label": "Home",
    "state": "active"
  }
}
```

```json
{
  "fn": "statusPill",
  "args": {
    "label": "Healthy",
    "tone": "success"
  }
}
```

```json
{
  "fn": "button",
  "args": {
    "label": "Deploy",
    "variant": "primary"
  }
}
```

```json
{
  "fn": "metric",
  "args": {
    "label": "Latency",
    "value": "8 μs",
    "valueStyle": "technical"
  }
}
```

```json
{
  "fn": "topologyMap",
  "args": {
    "nodes": [...],
    "edges": [...],
    "selectedNode": "studio-north"
  }
}
```

The semantic API should feel like designing a product, not reverse-engineering the plugin schema.

# 5. Add a real topology visualization primitive

EXO is fundamentally a distributed-compute product.

A topology map should be a first-class primitive instead of manually assembled rectangles and lines.

## Required capabilities

```text
Node
Node type
Memory
Compute capability
Health
Connection
Bandwidth
Latency
Selected state
Warning state
Placement state
Model shard
```

### Example

```json
{
  "fn": "topologyMap",
  "args": {
    "nodes": [
      {"id":"north","label":"Studio North","memory":"192 GB"},
      {"id":"south","label":"Studio South","memory":"192 GB"},
      {"id":"mac","label":"Aria MacBook","memory":"64 GB"}
    ],
    "edges": [
      {"from":"north","to":"south","latency":"8 μs","bandwidth":"8.7 GB/s"}
    ],
    "center": "EXO"
  }
}
```

The layout engine should route edges automatically and prevent overlapping labels.

# 8. Improve the visual refinement loop

The ideal workflow is:

```text
Plan
 ↓
Compose
 ↓
Create
 ↓
Render
 ↓
Visual judgement
 ↓
Structural review
 ↓
Fix
 ↓
Render again
 ↓
Final QA
```

The plugin already has pieces of this. They need to be connected into one workflow.

## Add

```ts
refine_screen({
  target,
  visualGoals: [...],
  preserve: [...],
  maxIterations: 3
})
```

The refinement engine should compare renders between iterations and identify:

```text
visual imbalance
empty-space imbalance
information density
alignment
hierarchy
button prominence
contrast
repetition
component consistency
```

# 9. Add visual-diff support

The current render tool is excellent but the agent has no native concept of:

> “What changed visually?”

Add:

```ts

```

Return:

```text
layout delta
new/removed regions
movement heatmap
density change
colour change
text hierarchy change
```

This would make iterative polish dramatically stronger.

```text
Composition             9.2/10
```

# 11. Strengthen design_guard

EXO-specific rules should remain machine-checkable.

Required rules:

```text
No manual device pairing
No manual network selection
No manual shard placement as default
No chat-first homepage
No generic 3-card SaaS dashboard
No unnecessary rounded-card stacking
Model fit must use cluster context
Topology must explain relationships
Integrations must use provider / endpoint / profile concepts
```

Add visual rules too:

```text
Primary action must be visually dominant
Selected state must be unambiguous
Topology must be legible without colour alone
Runtime values must use technical typography
Critical states must have text labels
```

# 12. Improve accessibility checks

Review currently catches some useful problems, but the system should also inspect:

```text
WCAG AA text contrast
focus states
keyboard target size
icon-only controls
semantic labels
colour-only state communication
long-content wrapping
minimum readable technical text size
```

For desktop EXO, use a minimum visual target of 44px for interactive controls where appropriate.

# 15. Better plan_screen → design_runtime integration

Current plan_screen is useful because it forces the agent to identify the primary decision.

The next step should be automatic conversion:

```text

      ↓
validated composition
      ↓
design_runtime()
      ↓
render
      ↓
review
```

Do not require the model to manually translate the plan into another coordinate system.

# 19. Definition of high-quality output

A screen should not be considered finished because:

```text
it has all the required text
it passes basic geometry checks
it technically renders
```

It should be considered finished when:

```text
The primary decision is obvious within 2–3 seconds.
The visual hierarchy is intentional.
The composition has a dominant focal relationship.
The information density feels purposeful.
The interaction hierarchy is obvious.
The visual language matches the rest of EXO.
The design system is reused rather than duplicated.
The screen passes structural QA.
The screen has been rendered and visually reviewed.
```

That is the bar the plugin should target.
